# Mobile-First Responsive UI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the Compose password manager adapt cleanly to compact phone widths and expanded windows without duplicated insets or navigation overlap.

**Architecture:** Keep `AppNavHost` and all repositories unchanged. Centralize navigation, window-width branching, and top-level `PaddingValues` in `AppScaffold`; make each screen consume that contract once. Standalone search and editor routes get their own safe-area and IME handling.

**Tech Stack:** Kotlin, Jetpack Compose Material 3, Navigation Compose, existing Compose UI test stack, Gradle Wrapper 9.7.1, Android SDK 36.

**Spec:** `docs/superpowers/specs/2026-09-15-mobile-responsive-ui-design.md`

## Global Constraints

- Preserve the existing route names, ViewModels, repositories, Room entities, and user-visible behavior.
- Keep `D:\DevTools\Java\jdk-21.0.2` as the verified local Gradle JDK and the Tencent Gradle distribution source.
- Do not use fixed bottom compensations such as `PaddingValues(bottom = 96.dp)` to represent system or navigation insets.
- Every screen consumes its supplied root `PaddingValues` exactly once.
- Compact layouts must remain usable at 360.dp width; text may ellipsize or wrap, but controls may not clip or force horizontal scrolling.

### Task 1: Establish the responsive shell contract

**Files:**
- Modify: `app/src/main/kotlin/com/example/myandroid/ui/component/AppScaffold.kt`
- Modify: `app/src/main/kotlin/com/example/myandroid/ui/AppNavHost.kt` only if the shell signature needs explicit route metadata
- Test: `app/src/androidTest/kotlin/com/example/myandroid/ui/AppNavigationTest.kt`

**Interfaces:**
- `AppScaffold(selectedRoute: String, onRouteSelected: (String) -> Unit, content: @Composable (PaddingValues) -> Unit)` remains the public shell API.
- The shell owns the compact bottom navigation or expanded rail and passes one `PaddingValues` object to the active top-level screen.

**Interfaces:**
- Existing ViewModel calls and callbacks stay unchanged.
- Each screen consumes `contentPadding` once at its root and uses shared compact gutters.

- [ ] **Step 1: Add compact geometry assertions**

  Add Compose assertions for the vault and categories roots that verify the list container is displayed and the action content has a semantics node. Keep assertions semantic rather than pixel-specific so they survive font-scale changes.

- [ ] **Step 2: Remove duplicate and fixed compensation padding**

  In `VaultScreen` and `CategoryScreenV2`, keep the outer `contentPadding` on the root container, remove list `bottom = 96.dp`, and anchor the FAB relative to the already-padded shell area. In shared list items, keep text in a weighted column and constrain trailing action rows so long titles and secrets ellipsize rather than push controls off-screen.

- [ ] **Step 3: Normalize settings sections and actions**

  Make settings form rows wrap or stack on compact widths. Keep full-width fields inside the root gutter and avoid a fixed-width action row. Ensure `LazyColumn` content padding includes only local section spacing, not system-bar compensation.

- [ ] **Step 4: Run build and the focused UI assertions**

  Run `./gradlew.bat :app:testDebugUnitTest :app:assembleDebug`, then connected tests when an emulator is available. Expected result: no compilation errors and no content padding regression.
